Additional observed controls:

- `Suggest an outfit` and `Suggest an outfit with blue` admit the general path.
  `Suggest a casual style outfit` is style, whereas `Suggest a smart casual outfit`

- `I'm meeting friends for dinner` and `I'm going out for dinner` admit DN rules.
  Going out does not establish an outdoor environment.
- `I'm presenting at a university presentation` admits AP rules. `I'm being
  interviewed for a job, the dress code is smart casual` admits IP rules, contingent

- Turquoise and shoes are unsupported in the probed requests. A supported long-

The actual quota is **100 non-archived garment entries**, enforced separately at
upload/confirmation; it is not a promise that every stored entry is confirmed and
eligible. ConfirmedGarmentQuery still requires owner, available status, confirmed

For ordinary appearance policies, current reviewed style can be enough for a narrow
positive heuristic. Do not require collar/tailoring/condition, material, fit or every
context slot merely because those fields exist. In particular, missing appearance
observations must not prevent an everyday or existing academic recommendation.
If a requested code or activity needs a fact, that fact's Unknown still blocks it.

Current resolver malformed-declaration/context-root barriers can block inference
even when a particular corrupt subfield seems unrelated. That is an intentional
conservative accepted boundary, not permission to silently repair data or ignore
malformation. Retain it in the recommended batch. A future field-scoped malformed
evidence design should be separately specified and regression-tested, keeping any
identifiable applicable Deny. Irrelevant **absent optional** observations and corrupt
authoritative containers are different cases.

Keep review optional until evidence is needed, with a truthful image/value explanation.
Reuse one style review across approved contexts and keep occasion overrides optional.
Do not relabel a correct classic style as casual to obtain an output. Bulk attestation,
automatic backfill, AI confidence cutoffs and model-driven admission remain unapproved.
Later consented observation of real user-reviewed garments could assess review burden,
understanding of Unknown, appropriate labels and perceived usefulness. No such user
study or real fashion validation is supplied by author-labelled synthetic tests.

## 5. User workflow and response strategy

The current ordinary compact path is: successful keyed replay first; otherwise
interpret once; check approved request capability; acquire a strict snapshot;
prepare mandatory evidence; enumerate four structures; score valid candidates;
publicly verify the winner; lock/revalidate snapshots and atomically persist.
The UI shows one immutable successful recommendation or a controlled failure;
there is no current multi-turn clarification session.

| User experience problem | Proposed treatment / scope |
|---|---|
|Natural class/shopping/friends requests fail despite familiar occasion vocabulary.|Recommended everyday batch: bounded semantic frames plus explicit shared appearance bindings, not global glue-word expansion.|
|The same apparent casual request means style in one phrase and declared formality in another.|Retain current meanings. Show interpreted requirements; offer literal example phrases. A standalone `I want something smart casual` contract needs a separately approved ambiguity rule.|
|Generic unsupported message hides whether the intent, role, modifier or evidence failed.|Keep safe top-level outcomes but return/display approved reason and accounted-for condition, without raw exception text. Structured context already helps after successful parsing; parse failures currently have no successful frame. Broader token-level diagnostics are separate framework work.|
|A capability boolean can look like support for every role/code.|Add human-readable supported examples, limits and required context; a binding's presence is not admission of every request. No automatic text rewrite/submission.|
|Interview/presentation shorthand is understood but cannot produce an outfit.|List missing role/code explicitly, as the existing professional summary does. Suggest editing the draft/new request; do not guess a candidate/presenter.|
|New unknown evidence message can feel like a demand to tag all occasions.|Identify required reusable style or appearance facts; do not demand optional event tags or unrelated attributes. Existing AP 1.2.0 text also mentions interview observations generally, which can confuse an academic user; refine by binding if separately approved.|
|Family dinner, direct travelling and familiar paraphrases are rejected.|A later interpretation/usability increment can propose `having`, family scope and direct travel frames. Preserve inactive travel and unsupported context; a parser fix cannot authorise suitability.|
|No complete outfit versus no reliable evidence versus all candidates failing.|Keep those outcomes distinct. Do not say all wardrobe items are inappropriate merely because evidence is missing.|

Proposed stable strategy:

| State | Existing top-level outcome / behaviour |
|---|---|
|A: Supported, admitted and feasible|Selected: exactly one fully eligible ranked outfit, assumptions and explicit/inferred basis stored.|
|B: Admitted domain but mandatory context absent|PolicyUnavailable / required_context_missing: name the missing role/code/activity. No wardrobe-based guessing.|
|C: Understood but inactive or outside supported code/scope|PolicyUnavailable / capability_not_enabled, unsupported_dress_code or unsupported_constraint: state what is understood and what is unavailable.|
|D: Ordinary general outfit request|Use existing general rules only when that is what the user requested. A user may choose a new explicitly generic request; never silently remove a specific context.|
|E: No eligible complete outfit / insufficient facts / known failure|Retain NoEligibleGarments or structural outcomes, InsufficientEvidence, or NoMatchingCandidates respectively. Do not relax conditions or create partial outfits.|
|Meaning cannot be represented safely|UnsupportedRequest: identify a controlled condition category where possible, invite an edited request. Unknown modifiers/negation/alternatives do not disappear.|

A **pre-submission draft preview** could eventually explain interpreted fields and
missing slots while retaining one final keyed request. It would need its own UI/API
and stale-context review; no automatic wardrobe/model calls or new persistence are
implied. Multi-turn clarification is larger: define draft versus completed chat,
parent/child keys, edits, ownership, retries and immutable replay before implementing.
Neither is part of the recommended policy batch or implemented here.

## 6. Reusable architecture and separately proposed framework improvements

Use the existing taxonomy → compositional interpretation → capability/binding →
evidence resolver/compiler → prepared mandatory facts → unchanged scorer path.
New situations should add semantic data and explicitly approved applicability,
not event-specific pipelines or metadata namespaces. Existing reviewed-style set
membership, all/any composition and admitted owner-observation equality are reusable.
Only the policy's active predicates should be prepared for a request.

The current registry is deliberately closed: version/number of bindings, IDs,
rule IDs, code sets, parent scopes and professional expression shapes are checked
in Python as well as configuration. The shared parser also contains bounded
role/domain refinements. Thus new support is **not safely config-only today**.
Minimal validator changes are necessary; do not merely relax the count or allow
arbitrary JSON operators/classes.

Separate framework follow-ups, not prerequisites for every new event:

1. Separate reusable schema/operator validation from an explicit approved bundle
   activation envelope. Keep exact schema/references/count/depth/size bounds and
   server-only immutable bundle hashes; no executable JSON or unapproved activation.
2. Define semantic overlap/refinement centrally. Adding campus/university aliases
   must not turn a university presentation into ordinary campus attendance, or
   swallow work interview, fitness-class, ceremony, conditional or compound context.
   Preserve original spans and all meaningful leftovers.
3. Improve typed capability requirements/reason guidance and distinguish binding
   availability from request admission. Preserve old explanation versions/history.
4. Review field-scoped malformed evidence, source confidence and generic declaration
   expansion only with named evidence/storage owners. Do not duplicate style truth
   or trust unreviewed model probabilities.

The next batch needs only controlled new aliases/refinements, the existing set
predicate, three validated bindings and clear explanations. A registry rewrite,
new request model, generic confidence score, model download or new wardrobe writer
would unnecessarily enlarge it.

## 11. Performance, integration and regression risks

No full NFR benchmark or new capacity population ran. The existing compact kernel
prepares per-member occasion/formality tables before enumeration; the primary and
independent paths resolve roughly **2 × N × K** member conditions. With 100 eligible
snapshots and at most two suitability fields, this is up to 400 preparation calls,
plus bounded winner/public/explanation work. The retained Phase 3 call-count fixture
observed 404 resolutions and five compilations; this review does not claim a new
measurement or that every path always has precisely those counts.

Everyday style membership is constant-size. Adding registry entries does not increase
the four-structure search space `(upper × lower + one_piece) × (1 + outerwear)`.
Compile only the selected binding, not all situations per garment. No model/network/
DB calls or configuration loading belong inside enumeration. Several fresh evaluators
currently load/validate bundles outside the loop; do not call that literally one
compilation or add mutable global caches speculatively.

Focused future verification is needed for new grammar overlaps/remaining-text checks,
bundle startup validation, exact declaration projections, per-request call counts,
snapshot currency, explanation size and current-contract transitions. A measured
changed-path delta is justified only if a concrete concern emerges, using retained
100-garment inputs with declared observations. No latency guarantee follows from
unchanged weights; no need to repeat J-16 or lower quota.

Highest integration risks are silent campus/presentation refinement, natural/command
Deny bypass, accidental new formality projection for an unspecified code, broad
context-root malformed bypass, skipping outerwear, interpreting companions as fashion
evidence, and incompatible bundle/explanation selection. Keep separate primary,
independent and public checks plus locked writer revalidation. History/replay must
continue returning stored versions before current interpretation.
